## 이 문서의 전제

이 사이트는 **로그인·회원가입·결제가 없는 소개형 사이트**다. 사용자 입력을 받는 지점은 `/contact` 문의 폼 **하나뿐**이다.

따라서 아래 항목들은 **점검 대상이 아니다** (구조상 발생하지 않음):

- 계정 탈취 / 세션 관리 / 비밀번호 저장
- 사용자별 권한 관리 (내 데이터를 남이 보는 문제)
- SQL 인젝션 — 사용자 입력으로 쿼리를 조립하지 않음
- CSRF — 인증 쿠키가 없어 공격이 성립하지 않음
- 결제·카드정보 (기획서 4.6: 유료 요소 없음 확정)

대신 리스크는 **① 문의 폼 · ② 개인정보 취급 · ③ 계정 관리** 세 곳에 집중된다. 이 문서는 그 세 곳과, 이 프로젝트에만 있는 위험 2건을 다룬다.

**사용법** — A는 개발 방식을 정할 때, B는 개발 중에, C는 오픈 직전 QA(기획서 11장)에, D는 오픈 후 정기적으로 확인한다.

## A. 지금 결정해야 하는 것 — 나중에 고치기 어려움

> 개발 착수 전에 정해야 하고, 코드 구조가 여기에 따라 달라진다.

### 🔴 A-1. 파트너사·병원 정보를 마크업에 남기지 않는다

**문제**
기획서 5.1 S5 / 4.2는 로고 슬롯을 마크업에 넣고 `display:none` 처리하라고 지시한다. 그런데 같은 문서 4.2·4.5·10장의 확정사항은 **"협업 상대사 사명·업종·규모 전면 미표기"**, **"병원 실명·소재지 비노출"** 이다.

`display:none` 은 화면에서만 안 보일 뿐 **브라우저 소스 보기로 전부 노출되고, 검색엔진도 읽는다.** 이미지 파일명(`/partners/○○.svg`), `alt` 텍스트, HTML 주석 어디든 사명이 들어가면 미노출 원칙이 깨진다. B2B 영업 사이트에서 이게 발견되면 파트너사 신뢰 문제로 직결된다.

**조치**

- [ ] 로고 슬롯은 `display:none` 이 아니라 **조건부 렌더링(`false`)으로 아예 그리지 않는다**
- [ ] 컴포넌트 구조·props 타입만 정의해 두면 확장성 목적은 그대로 달성된다
- [ ] 플레이스홀더에 **실명·실제 파일 경로·업종 힌트를 넣지 않는다**
- [ ] HTML 주석에도 사명을 쓰지 않는다 (`{/* 아더사이더 로고 자리 */}` 같은 것도 안 됨 — JSX 주석은 안전하지만 HTML 주석은 그대로 나감)

**확인 방법**

```bash
# 빌드 산출물 전체에서 미노출 대상 문자열 검색 — 0건이어야 함
npm run build
grep -ri "병원명\|파트너사실명\|상급종합" .next/ out/ 2>/dev/null
```

배포 후 브라우저에서 `Ctrl+U`(소스 보기) → `Ctrl+F` 로 각 사명 검색.

### 🔴 A-2. 저장소는 계속 private으로 둔다

**문제**
사이트가 공개된다고 코드까지 공개할 이유는 없다. 이 프로젝트는 특히 그렇다 — 개발 과정에서 카피 초안·주석·커밋 메시지에 병원명이나 파트너사명이 **한 번이라도** 들어가면 커밋 히스토리에 영구히 남는다. 나중에 지워도 히스토리에는 남고, public이었다면 이미 크롤링된 뒤다.

**조치**

- [ ] `eunji-eunji/fluxlabs-homepage` private 유지 (오픈 후에도)
- [ ] Settings → General → Danger Zone 의 "Change visibility" 를 건드리지 않는다
- [ ] 협업자 추가 시 필요한 최소 권한만 부여 (디자이너는 Write면 충분, Admin 불필요)

**확인 방법**

```bash
gh api repos/eunji-eunji/fluxlabs-homepage --jq '{private, visibility}'
# {"private": true, "visibility": "private"} 이어야 함
```

**⚠️ 별건 — 저장소 소유자가 개인 계정이다**
현재 이 저장소는 회사 조직(Organization)이 아니라 **개인 계정 `eunji-eunji` 소유**다. 회사 공식 홈페이지가 개인 계정 아래 있으면 담당자 변경·퇴사 시 소유권 이전 문제가 생긴다. 오픈 전에 회사 Organization을 만들어 이관하는 것을 권장한다 (이관해도 URL 리다이렉트는 유지됨). 대표님/이영광 이사님 판단 사항.

- [ ] 회사 Organization 생성 및 저장소 이관 여부 결정

### 🔴 A-3. 문의 내용을 저장소에 적재한다 (메일만으로는 안 됨)

**문제**
부록 A 제3조는 **"문의 응대: 처리 완료 후 3년 보관 후 파기"** 로 확정되어 있다. 그런데 5.5의 권장안대로 SMTP 메일 발송만 하면, 데이터가 개인 메일함에 흩어져서 **3년 뒤 파기 의무를 이행할 방법이 없다.** 방침 문서와 실제 운영이 어긋나는 상태가 된다.

**조치**

- [ ] 서버리스 함수 → ① 저장소 적재 + ② 알림 발송 **두 가지를 모두** 수행
- [ ] 저장소는 Supabase / Google Sheets 수준이면 충분 (문의량 월 5건 목표)
- [ ] 각 레코드에 `created_at` 을 남겨 3년 경과분을 식별할 수 있게 한다
- [ ] 파기 절차를 문서로 남긴다 (누가, 언제, 어떻게)

## B. 개발 중 — 코드에서 지킬 것

### B-1. 문의 폼 남용 방어 3종

발생 확률이 가장 높은 실제 사고다. 공개된 폼은 봇이 며칠 안에 찾는다. 진짜 피해는 메일함 도배가 아니라 **메일 발송 서비스 한도 소진 + 발송 도메인의 스팸 리스트 등재**이며, 그 경우 `@fluxlabs.co.kr` 로 나가는 **회사 메일 전체의 도달률이 떨어진다.**

- [ ] **허니팟 필드** — 사람 눈에 안 보이는 입력란을 두고, 값이 채워져 있으면 조용히 무시 (기획서 5.5가 reCAPTCHA 대안으로 이미 허용)
- [ ] **Rate limit** — IP당 시간당 N건 제한 (예: 5건). 월 5건 목표에 충분
- [ ] **서버 측 길이·형식 검증** — 문의 내용 10~2000자, 이메일 형식 (5.5 정의). **클라이언트 검증만으로는 안 된다** — 봇은 브라우저를 안 쓴다

### B-2. 폼을 스팸 릴레이로 쓰지 못하게

- [ ] **수신자 주소를 서버 코드에 하드코딩** — 요청 값(`to`, `recipient` 등)에서 절대 받지 않는다
- [ ] 메일 본문을 **HTML이 아닌 텍스트**로 발송 (또는 전체 이스케이프)
- [ ] 발신자 이름·제목에 사용자 입력을 그대로 넣지 않는다 (헤더 인젝션 방지 — 개행 문자 제거)

### B-3. 저장 시 인젝션

- [ ] **Google Sheets에 적재한다면 CSV 인젝션 주의** — `=`, `+`, `-`, `@` 로 시작하는 값은 수식으로 실행된다. 값 앞에 `'` 를 붙이거나 DB를 쓴다
- [ ] Slack 알림을 쓴다면 사용자 입력에 대한 마크다운/멘션(`@channel`) 이스케이프

### B-4. 개인정보가 로그에 남지 않게 (부록 A 제8조 안전성 확보 조치)

- [ ] **서버리스 함수에서 request body를 로그로 출력하지 않는다** — `console.log(req.body)` 금지
- [ ] 에러 트래킹(Sentry 등)을 붙인다면 body를 스크러빙 설정
- [ ] 에러 응답에 입력값을 그대로 되돌려주지 않는다

**확인 방법**

```bash
grep -rn "console\.log" app/api/ src/app/api/ 2>/dev/null
```

배포 후 폼 1건 제출 → Vercel 대시보드 → Logs 에서 이름·이메일이 찍히는지 육안 확인.

### B-5. 비밀키가 브라우저로 새지 않게

Next.js에서 환경변수에 **`NEXT_PUBLIC_` 접두사를 붙이면 브라우저 번들에 그대로 들어간다.** 신입이 가장 자주 하는 실수다.

- [ ] SMTP 비밀번호 / 메일 API 키 / DB 키에 `NEXT_PUBLIC_` 을 **붙이지 않는다**
- [ ] 카카오맵 JS 키는 원래 노출되는 종류라 `NEXT_PUBLIC_` 이 맞지만, **카카오 개발자 콘솔에서 도메인 화이트리스트를 반드시 등록** (안 하면 남이 우리 쿼터를 쓴다)
- [ ] `.env*` 가 `.gitignore` 에 포함되어 있는지

**확인 방법**

```bash
npm run build
grep -r "SMTP\|SECRET\|_KEY" .next/static/ 2>/dev/null   # 0건이어야 함
git check-ignore -v .env.local                            # 무시되는지 확인
```

### B-6. XSS — 정적 사이트라도 딱 한 군데

React는 기본적으로 이스케이프하므로 대부분 안전하다. 뚫리는 곳은 하나뿐이다.

- [ ] **`dangerouslySetInnerHTML` 을 쓰지 않는다.** MDX 렌더링에서도 raw HTML 허용 옵션을 켜지 않는다
- [ ] 로고 SVG를 인라인으로 넣을 때(8.3의 `fill` 전환 요구사항) 신뢰된 파일만 사용

### B-7. 보안 헤더

정적 사이트라도 `next.config` 몇 줄이면 끝난다. Lighthouse Best Practices 점수에도 반영된다.

- [ ] `Content-Security-Policy` (GA4·네이버 애널리틱스·카카오맵 도메인 허용 필요)
- [ ] `X-Frame-Options: DENY` — 클릭재킹 방지
- [ ] `X-Content-Type-Options: nosniff`
- [ ] `Referrer-Policy: strict-origin-when-cross-origin`
- [ ] `Strict-Transport-Security`

**확인 방법** — 배포 후 https://securityheaders.com 에 도메인 입력, 또는

```bash
curl -sI https://fluxlabs.co.kr | grep -i "content-security\|x-frame\|strict-transport"
```

## C. 오픈 전 점검 (기획서 11장 QA 단계)

### C-1. 노출 관련

- [ ] **A-1 재확인** — 배포된 사이트 소스 보기에서 파트너사·병원 관련 문자열 0건
- [ ] **Vercel 프리뷰 배포 보호** — 프리뷰 URL은 주소만 알면 누구나 본다. 확정 전 카피·미완성 페이지가 노출된다. Vercel → Settings → Deployment Protection 활성화 (플랜별 제공 범위 확인 필요)
- [ ] **`/news` 등 미완성 라우트에 `noindex`** — GNB에 없어도 크롤러는 찾는다. 빈 페이지가 색인되면 기획서 1.4의 "검색 1위" 목표에 해롭다
- [ ] `robots.txt` 가 의도한 대로인지 확인 (프리뷰 도메인은 전체 차단)
- [ ] 소스맵이 프로덕션에 올라가지 않는지

### C-2. 폼 실전 테스트

- [ ] **직접 100번 연속 제출해본다** — rate limit이 실제로 도는지 확인하는 가장 빠른 방법
- [ ] 허니팟 필드에 값을 넣고 제출 → 차단되는지
- [ ] 문의 내용에 `=1+1`, `<script>alert(1)</script>`, `@channel` 넣고 제출 → 저장소·알림에서 안전하게 처리되는지
- [ ] 2000자 초과 입력 → 서버에서 거부되는지 (브라우저 검증 우회해서 `curl` 로 직접)
- [ ] 실패 시 대표 이메일 안내가 뜨는지 (5.5 정의)

### C-3. 개인정보 관련

- [ ] 동의 체크박스 없이 제출 불가한지
- [ ] `[전문 보기]` → `/privacy` 링크 동작
- [ ] 푸터의 **개인정보처리방침 링크 볼드 처리** (법적 의무 — 기획서 3.2)
- [ ] 부록 A 제5조 처리위탁 표에 **실제 사용 사업자가 전부 기재**되었는지
- [ ] 국외 사업자를 쓴다면 **"개인정보의 국외 이전" 조항**이 추가되었는지 (이전받는 자·국가·시점·항목·목적·보유기간 전부)
- [ ] 개인정보 보호책임자(이영광 개발총괄이사) 정보 노출 확인
- [ ] **방침·약관 시행일(2026-08-31)과 실제 오픈일이 맞는지** — 오픈이 늦으면 두 문서 날짜를 함께 조정해야 함

### C-4. 비밀정보 유출

- [ ] `git log -p` 로 `.env`, 키, 비밀번호가 커밋된 적 없는지
- [ ] GitHub Settings → Code security → **Secret scanning 활성화** (private 저장소에서도 가능)
- [ ] Vercel 환경변수가 Production/Preview/Development 별로 올바르게 분리되어 있는지

- [ ] Google(GA4/서치콘솔) 계정 2FA
- [ ] **협업자 `kim-dong-uk97` 도 2FA를 켜게 한다** — Write 권한이 있으므로 그쪽이 뚫리면 저장소가 뚫린다
- [ ] 복구 코드를 **인증 앱과 같은 기기에 두지 않는다** (비밀번호 관리자 또는 인쇄 보관)

## E. 구현 후 남은 잔여 항목 (2026-08-13 추가)

개발 착수 후 확인된, **현 단계에서 완전히 해소하지 못한 항목**이다.
기획서 대비 구현 차이 전반은 `docs/deviations.md` 에 정리했다.

### E-1. CSP `script-src` 에 `'unsafe-inline'` 이 남아 있다 (B-7 관련)

Next.js 가 하이드레이션 부트스트랩을 인라인 `<script>` 로 주입하기 때문이다.
제거하려면 middleware 에서 nonce 를 발급해야 하는데, middleware 는 전 라우트를
동적 렌더링으로 만들어 기획서 7.3 의 성능 목표(SSG)를 잃는다.

수용 근거: 사용자 입력 지점이 문의 폼 하나뿐이고, React 가 기본 이스케이프하며,

### E-2. Rate limit 이 프로세스 메모리 기반이다 (B-1 관련)

서버리스는 인스턴스가 여러 개 뜨고 수시로 재활용되므로 카운터가 공유되지 않는다.
실제 허용량이 설정값(시간당 5건)보다 늘어날 수 있다.

1차 방어선은 허니팟과 시간 트랩이며, 로컬 검증에서 정상 동작을 확인했다.

      `checkRateLimit` 시그니처를 유지하면 호출부 수정 불필요
